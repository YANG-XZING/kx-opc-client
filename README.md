# kx-opc-client

多炉台 OPC UA 采集客户端。它按 `furnaces.json` 里配置的炉台（单个 IP 或 IP 范围），订阅每台炉台上 `KXOpcServices`（OPC UA 服务端）的全部点位，
**服务端心跳每变化一次（约每秒一轮），就把全部点位写成 TDengine 里的一行**。
运行环境是 CentOS 7，以 systemd 服务形式部署。

## 处理流程

```
furnaces.json ──► 每台炉台一个采集协程 ──► 分发 ──► TDengine 存储端（全部炉台，每秒批量写一次）
 （IP 范围先探测端口；│ 连接 → 读取点位目录（每 10 秒刷新）→ 订阅  └─► 以后的 MySQL 存储端（指定炉台）
  定期重读，只增不减）│ 服务端推送变化 → 合并进各点位最新值
                    │ 心跳变化 → 写一行全量；心跳不变（上位机断开）→ 不写
                    │ 断线 → 5s 到 60s 指数退避重连
```

1. 启动时读取 `config.yaml` 和 `furnaces.json` 并校验，配置有错误直接报错退出；
2. 单独写出的 IP 直接加入采集；IP 范围里的 IP 先探测 OPC 端口，能连通的才加入。每台炉台一个采集协程，互不影响；
3. 每台炉台订阅全部点位，心跳每变化一次产生一行全量快照（见下面“取数与写入方式”），交给分发器，分发器按各存储端的过滤条件投递到它们各自的队列；
4. TDengine 存储端每秒把所有炉台的数据合成一条多表 INSERT 写入；写不进去（TDengine 不可用）时这段时间的数据直接丢弃，不在内存里积压，恢复后接着写；
5. 定期（默认每天）重读 `furnaces.json`，并重新探测 IP 范围里还没在采集的 IP：新加的或新上线的炉台自动开始采集；删掉的 IP 继续采集，重启服务后才停止；
6. 收到停止信号后，先停采集，再把还没写的数据写完。

## 取数与写入方式

**订阅 + 心跳触发写入**：

1. 连上炉台后订阅全部点位，服务端在值变化时推送（推送间隔 100 毫秒）；刚订阅（含重连）时服务端先推送全部点位的当前值；
2. 客户端为每台炉台缓存各点位的最新值，每次推送都合并进缓存；
3. **服务端心跳 `HEART_DATETIME` 每变化一次，就写一行全量**：全部点位，本轮没变化的点位沿用上次的值（不写 NULL），`ts` 为心跳变化到达客户端的时刻；
4. 每次连上（含重连）后收到的第一个心跳是订阅时推送的当前值，不是新一轮采集，只作为基准、不写入，从下一次变化开始写（所以连上后约 1 秒才有第一行，上位机断开时重连也不会写出重复的旧数据）；
5. **每台炉台的 `ts` 按毫秒严格递增**：系统时钟被往回调时（比如虚拟机校时和 chronyd 互相打架），`ts` 不倒退，顺延到上一行之后 1 毫秒，等系统时钟追上来再恢复，避免 TDengine 里相同 `ts` 的行被覆盖、重叠的 `ts` 打乱顺序。程序重启后从当时的系统时间重新开始。

为什么按心跳写：服务端每轮先写各点位、最后刷新心跳（实测一轮写入约 460 毫秒，心跳之后至多 1 毫秒内还有个别点位），所以心跳一变化，这一轮的数据已经到齐，收到即写，不需要等待；上位机断开时心跳不再变化，也就不再写入，不会有冻结的重复数据。

- **周期跟随服务端**：服务端一轮约 1.01 秒（取数 + `Sleep(1000)`），所以大约每秒一行，`ts` 的毫秒部分不固定，每隔 1~3 分钟会少一秒的行；
- 订阅依赖服务端在赋值后调用 `ClearChangeMasks`，新版服务端已经支持。
- **服务端通讯状态 `HMIDataErrorID`**（0 正常 / 10 通讯失败 / 20 解析错误）：它是普通点位，每行都会存；但通讯失败时心跳不变、不会写行，所以 TD 里很少看到非 0 的值。客户端在它**变化时**记一条日志（`服务端与上位机通讯异常 comm_status="10 通讯失败"` / `服务端与上位机通讯恢复`），心跳停止的警告里也会带上当时的状态码，用来判断是哪种原因断的。
- **服务端刚启动**：首次采集完成前，心跳是初始值 `"0"`、状态码是初始值 10、其他点位都是初始值。此时客户端**不写入**（避免把一行 0 写进 TD），日志只记一条 `服务端启动中，等待首次采集`，不报通讯失败；首次采集完成后自动开始写入。通讯状态码不论服务端发的是 Float、Int16 还是数字字符串都能识别。

### 服务端热更新点位（增加、删除、重建）

服务端重载 `HMI_Value.XML` 时会增删点位；点位的类型、文件夹或来源变了时，会**删掉旧节点、用同一个 NodeId 重建**。服务端做这些事时**不会给客户端任何通知**（旧的监控项只是从此不再推送），所以客户端自己检查：

| 情况 | 客户端怎么发现 | 怎么处理 | 多久 |
|------|------|------|------|
| 新增点位 | 每 10 秒读一次点位目录 `VarNodeIds` | 为新点位建监控项，第一次有值时自动加列 | ≤ 10 秒 |
| 删除点位 | 同上 | 删掉它的监控项，之后的行不再包含它（列保留，新行里为 NULL） | ≤ 10 秒 |
| 删除后同名再加回来 | 同上 | 当作新增，重新建监控项 | ≤ 10 秒 |
| 重建节点（改了类型等） | 每 30 秒直接读一遍全部点位的当前值，和订阅收到的值比较：不一样、并且隔一轮检查仍没收到推送的，就是订阅失效 | 只给这几个点位重新建监控项，最新值先换成直接读到的值；不丢行 | 30～60 秒 |

正常的监控项在值变化后 1 秒内就会推送，不会被误判。在这之前，删除的点位最多沿用旧值约 10 秒、重建的点位最多约 1 分钟。日志：`点位变化 新增=… 删除=…`、`点位订阅失效（服务端重建了节点），已重新订阅 点位=…`。

## 写入可靠性：尽量不丢数据

每秒把所有炉台攒下的行拼成一条多表 INSERT 写入（效率高）。为了不让个别问题拖垮整批，按下面的层次处理：

1. **文本值先清洗**：PLC 的字符串常是定长缓冲区，后面补 `\0`（实测 AA065 的 `PLC_VERSION` 是 `"V6.17.1.1-KA250601-1.1.0\x00\x00\x00\x00\x00\x00"`）。`\0` 会让 TDengine 认为字符串没结束、整条 INSERT 报语法错误。写库前去掉控制字符（换行、制表换成空格）和非法 UTF-8 字节。
2. **某个点位的值有问题**（TDengine 报语法 / 数据错误）：整批先按炉台拆开重写，再按行；有问题的那一行**逐个去掉一个文本点位试写，只去掉有问题的那个，同一行的其他点位照常写入**；都不行再去掉类型和列不一致的点位、再去掉全部文本点位；还写不进去（如时间戳超出 KEEP 范围，和点位无关）才跳过这一行。日志 `数据有问题，只去掉有问题的点位…` / `…这一行跳过` 会带上点名和原始值（`%q` 显示，能看出不可见字符），同一台炉台每 10 分钟最多记一次；状态日志里有 `去掉坏点位_1m`、`跳过坏行_1m`。
3. **TDengine 不可用**（连不上、超时、服务端未就绪）：数据**落盘暂存**到 `config.yaml` 的 `tdengine.spool_dir`（`/home/kx-opc-client/data`，最多 `spool_max_mb` 2048MB），恢复后按时间顺序自动补写（每秒最多花 3 秒补写，不耽误新数据），补写完删除文件；程序重启后也会接着补写。升级时 `install.sh` 会保留现场的 `config.yaml`，如果里面还没有这两项，会自动加上（原文件先备份），并按配置创建目录、交给服务用户 `kxopc`。暂存目录不可写时只记一条错误，采集和正常写库不受影响（只是数据库不可用期间的数据没法暂存）。状态日志里有 `暂存_1m`、`暂存积压`、`补写_1m`。暂存目录满了才会丢弃新数据（`丢弃_1m`）。同一炉台同一 `ts` 重复写入会覆盖，补写中途再断开重来也不会出现重复行。
4. 拆开后一行都写不进去，按 TDengine 本身有问题处理（第 3 条），不会把整批当成坏数据丢掉。

排查某台炉台到底上报了什么值：`./kx-opc-client -probe <炉台IP>` 连上这台炉台读一遍全部点位，打印每个值的原样内容，含不可见字符或非法编码的文本点位会标出并附十六进制；只读，不写库，不影响正在运行的采集服务。

## TDengine 表结构

```
kx_opc                          ← 库，不存在时程序按 database_options 自动创建
└── opc_data                    ← 超级表，程序自动创建
    ├── opc_10_65_108_12        ← 每台炉台一张子表，首次写入时自动创建
    └── ...
```

| 列 | 类型 | 说明 |
|---|---|---|
| `ts` | TIMESTAMP | **数据采集时间**：服务端心跳变化到达客户端的时刻（客户端时间，精确到毫秒） |
| `` `HEART_DATETIME` ``、`` `MELT_TEMP_PV` `` … | 按 OPC 节点类型 | 每个点位一列，**列名 = 点名，保留原始大小写**；出现新点位时自动 `ALTER STABLE ADD COLUMN` |
| `device_id` | 标签 VARCHAR(64) | 炉台号（确定规则见“配置 → 炉台号怎么确定”） |
| `device_ip` | 标签 VARCHAR(64) | 炉台 IP |

- **不需要提前建库建表**。DBA 想手工建的话可以参考 `sql/tdengine/opc_data.sql`。
- **每一列都带压缩选项**：建表时的 `ts`、心跳列，以及之后自动添加的每个点位列，都带 `COMPRESS 'zstd' LEVEL 'high'`（`config.yaml` 的 `compress`、`compress_level` 可改）。启动时如果发现已有列的压缩方式和配置不一致，会自动 `ALTER STABLE ... MODIFY COLUMN ... COMPRESS ...` 改过来；改压缩只影响之后落盘的数据，已有数据要执行一次 `COMPACT DATABASE kx_opc` 才会重新压缩。标签不支持列压缩。
- **建库参数**（`database_options`，只在库不存在时生效）：`MAXROWS 40000 MINROWS 1000` 让数据块尽量大、压缩率更高，`KEEP 1095d` 保留 3 年。
- **列名区分大小写**：建列和写入时列名都用反引号包裹，查询时也要用反引号，比如 `` SELECT `HEART_DATETIME` FROM ... ``。
- **列类型按 OPC 节点类型建**（即服务端 `HMI_Value.XML` 里的 `type`），值按原类型写入，数值列可以直接计算：

  | OPC 类型 | TD 列类型 |
  |---|---|
  | Boolean（bit/bool） | BOOL |
  | Float | FLOAT |
  | Double | DOUBLE |
  | SByte / Int16 / Int32 / Int64 | TINYINT / SMALLINT / INT / BIGINT |
  | Byte / UInt16 / UInt32 / UInt64 | 对应的 `UNSIGNED` 类型 |
  | DateTime | TIMESTAMP |
  | String 及其他 | VARCHAR(`value_length`)，默认 256 字节，超长截断 |

- **列类型建好后不再变**：列在这个点位第一次有值时按当时的类型建，之后服务端改了类型（或各炉台服务端版本不一致，同一点位类型不同），值**按原来的列类型转换后写入**：
  - 能转换的照常写：数字写进 VARCHAR 列变成文本，数字字符串写进数值列，整数列收到小数四舍五入；
  - 转换不了的写 NULL：数值列收到非数字的字符串，时间列收到数字等；
  - **超出列类型范围的写 NULL**：TINYINT 收到 1000、无符号列收到负数、FLOAT 列收到超过 3.4e38 的数。不写 NULL 的话 TDengine 会报错，整行都写不进去；
  - 每个点位每种新类型记一条 `点位类型和列不一致` 日志，写明列类型、收到的类型、值和怎么处理的；写了 NULL 或丢了精度（Double 存进 FLOAT 列、数值转成布尔）的记 WARN；写成 NULL 的值在状态日志里计入 `类型不符写空_1m`。
  - 需要按新类型存时手工处理：停掉客户端 → `ALTER STABLE ... DROP COLUMN` 删掉这一列（这一列的旧数据会一起删掉）→ 启动客户端，会按新类型重新建列；或者在服务端改回原类型。

- 点名里字母、数字、下划线以外的字符会替换成 `_`；数字开头，或者和 `ts`、`device_id`、`device_ip` 同名的，会加 `p_` 前缀。
- 单行长度上限是 48KB：按每列 66 字节算，最多大约 740 个点位。超出的点位，或者替换字符后列名冲突的点位（比如 `Temp-1` 和 `Temp_1`）会被跳过并打日志。

## 配置

一共两个文件，都在 `/opt/kx-opc-client/` 下。

**`furnaces.json`：要采集的炉台，没配置到的 IP 一律不连。**

```json
{
  "port": 4840,
  "areas": [
    { "prefix": "10.65.108.", "area": "A" },
    { "prefix": "10.65.104.", "area": "C" }
  ],
  "furnaces": [
    "10.65.108.1-254",
    "10.65.104.20"
  ],
  "exclude": [
  ]
}
```

| 字段 | 说明 |
|---|---|
| `furnaces` | 要采集的炉台，两种写法可以混用：<br>**单个 IP**（如 `10.65.104.20`）：一定采集，连不上就一直重连；<br>**IP 范围**（如 `10.65.108.1-254`，只支持最后一段）：只采集范围里 OPC 端口能连通的 IP，连不通的跳过，下次重读清单时再探测 |
| `exclude` | 不采集的 IP，比如范围里的服务器、交换机。可以不写 |
| `areas` | 网段前缀规则（可选）：上位机没有配置设备名时，炉台号 = 区号 + IP 最后一段，比如 `10.65.108.12 → A12`。IP 不属于任何区也可以采集 |
| `port` | 炉台 OPC 端口（服务端 App.config 里的 OpcPort），默认 4840 |

子表名 = `opc_` + IP，比如 `opc_10_65_108_12`。格式错误、单个 IP 重复、单个 IP 又写进了 `exclude`，都会报错并指出是哪一条。范围之间重叠，或者范围包含了单独写出的 IP，会自动去重。

**全量采集**：每个区写一行范围即可，比如 `"10.65.108.1-254"`。同时建议把 `config.yaml` 里的 `furnaces_reload_interval` 改成 `1h`，新上线的炉台 1 小时内就会自动加入。范围探测只是 TCP 连一下 OPC 端口就断开，1500 个 IP 几秒钟就能探完，对服务端没有影响。

**`config.yaml`：TDengine 连接、炉台清单重读周期、心跳超时、日志**，每一项都有注释，一般不用改。

**炉台号怎么确定**（连上炉台后确定，按顺序）：

1. **上位机配置的设备名**：服务端 OPC 应用名为 `LintonKXOpcServer_{设备名}`，设备名来自上位机的 `LocalDeviceConfig.dat`；
2. 上位机上报的是**默认值 `3G14`**（说明上位机缺少配置文件），改用 `areas` 的网段前缀规则；
3. 上位机是 `3G14`、又没有匹配的网段前缀时，炉台号就用 `3G14`。子表名和 `device_ip` 标签都按 IP 区分，炉台号重复不影响数据区分。

炉台号变化时（比如上位机补上了配置文件，重连后设备名变了），日志会记一条“炉台号变更”，TD 子表的 `device_id` 标签也会跟着更新。

改完以后先校验（会实际探测一次 IP 范围，列出将要采集的每台炉台的端点、子表名和网段前缀炉台号，不启动采集）：

```bash
sudo -u kxopc /opt/kx-opc-client/kx-opc-client -check
```

新增炉台在下次重读清单时自动生效；想立即生效、或者删掉炉台后要停止采集，就重启服务：

```bash
sudo systemctl restart kx-opc-client
```

## 构建与部署

在开发机上（Windows 用 Git Bash）构建：

```bash
./scripts/build.sh 1.0.0
```

把生成的 `dist/kx-opc-client-1.0.0-linux-amd64.tar.gz` 拷到 CentOS 7 上，解压：

```bash
tar xzf kx-opc-client-1.0.0-linux-amd64.tar.gz
```

安装：

```bash
cd kx-opc-client-1.0.0-linux-amd64 && sudo ./deploy/install.sh
```

编辑 `/opt/kx-opc-client/furnaces.json`，校验通过后启动：sudo vi /opt/kx-opc-client/furnaces.json  sudo vi /opt/kx-opc-client/config.yaml

```bash
sudo systemctl start kx-opc-client
```

查看日志：

```bash
journalctl -u kx-opc-client -f
```

日志说明（每台炉台的日志都带 `furnace=炉台号`，连上之前用 IP）：

一切正常是一行 INFO；有任何异常就变成 WARN，并且只把异常项加在后面，看这一行就知道问题出在哪一层、哪几台炉台：

```
运行状态 在线=8/8 写入_1m=472 数据库=正常
运行状态 在线=8/8 写入_1m=472 数据库=正常 去掉坏点位_1m=59
运行状态 在线=8/8 写入_1m=413 数据库=正常 连着没入库=AA065
运行状态 在线=7/8 写入_1m=0 数据库=不可用(12m3s) 断开=BB003 暂存_1m=420 暂存积压=3.1MB
```

| 状态日志里的项 | 说明（问题出在哪） |
|------|------|
| `在线=8/8`、`写入_1m` | 连着的台数 / 总台数，最近一分钟写进库的行数（每台约每秒一行） |
| `断开=…` / `连接中=…` | 连不上这些炉台：采集端到炉台的网络，或炉台上的 OPC 服务 |
| `心跳停=…` | 连着，但上位机心跳不变（上位机没在采集） |
| `连着没入库=…` | 连着、心跳也在走，这一分钟这台却一行都没写进库：多半是这台的数据有问题，看下面的「点位值有问题」日志 |
| `数据库=不可用(时长)` | 写不进 TDengine（连不上、超时）；期间数据落盘：`暂存_1m`、`暂存积压`，恢复后自动补写：`补写_1m` |
| `去掉坏点位_1m` / `跳过坏行_1m` / `丢弃_1m` | 有数据没完整入库：去掉了有问题的点位后入库 / 整行写不进去跳过 / 暂存满了丢弃 |
| `类型不符写空_1m` | 服务端改了点位类型，值转换不了列类型（或超出范围）而写成 NULL 的个数：看「点位类型和列不一致」日志 |

其他日志只在**状态变化时**记一条（不会每次重试都刷屏）：

| 日志 | 级别 | 什么时候出现 |
|------|------|------|
| `开始采集 furnaces=… tdengine=…` | INFO | 启动时一条：采集的炉台数、TD 地址（不含密码） |
| `已连接 炉台=B04 ip=… 炉台号来源=上位机 点位数=80` | INFO | 每台炉台第一次连上 |
| `无法连接，持续重试` / `连接断开，自动重连` / `重连成功 断开了=15s` | WARN / INFO | 连不上或断线只记开始一次（之后的重试在 debug 级别），重新连上时带断了多久 |
| `心跳停止变化，暂停写入` / `心跳恢复，继续写入 停了=…` | WARN / INFO | 上位机数据中断超过 `heartbeat_timeout` / 恢复 |
| `服务端与上位机通讯异常 通讯状态=…` / `通讯恢复` | WARN / INFO | `HMIDataErrorID` 变为非 0 / 回到 0；`服务端启动中，等待首次采集` 是服务端刚启动 |
| `点位值有问题，只去掉这个点位，其他点位照常入库 炉台=AA065 点位=PLC_VERSION="V6…\x00\x00"` | WARN | 某个点位的值写不进库：带炉台、点名和原始值（不可见字符也显示出来），同一台炉台每 10 分钟最多一条 |
| `这一行数据写不进去，跳过` | WARN | 去掉文本点位也写不进去（和点位无关，如时间戳超出范围） |
| `数据库写不进去，数据先落盘暂存…` / `数据库写入恢复 中断=… 暂存=…` / `落盘暂存的数据已全部补写` | WARN / INFO | TD 不可用 / 恢复 / 补写完 |
| `写库跟不上，队列已满，丢弃快照` | WARN | 写库速度跟不上采集（每 1000 条记一次） |
| `炉台号变更` / `点位变化 新增=… 删除=…` / `新增点位列` | INFO | 上位机设备名变了 / 服务端重载点位表增删了点位（超过 20 个只列前 20 个）/ 出现新点位自动加列 |
| `点位订阅失效（服务端重建了节点），已重新订阅 点位=…` | WARN | 服务端重建了这些节点（改了类型、文件夹或来源），旧监控项不再推送，已重新订阅 |
| `点位类型和列不一致 炉台=… 点位=… 列类型=FLOAT 收到类型=String 值=… 处理=…` | WARN / INFO | 服务端改了点位类型；有损（写 NULL、丢精度）是 WARN，无损转换是 INFO；每个点位每种类型只记一次 |
| `系统时钟被往回调，ts 顺延到上一行之后 回调了=6s` / `系统时钟已追上` | WARN / INFO | 服务器校时有问题 |
升级时重新执行 `install.sh` 即可，现场的 `config.yaml` 和 `furnaces.json` 会保留。

## 目录结构

```

internal/
  app/                      组装各模块：启动各炉台采集、定期重读清单、状态汇总、优雅停机
  config/                   config.yaml 与 furnaces.json 的加载、校验；IP 范围展开；IP → 子表名 / 网段前缀炉台号
  scanner/                  探测 OPC 端口能否连通，用于筛选 IP 范围中实际存在的炉台
  model/                    公共数据结构
  opc/                      OPC UA 会话：连接、读取点位列表、订阅推送（subscribe.go）
  collector/                一台炉台的采集循环：重连、确定炉台号、最新值缓存、心跳触发写入、状态判断
  storage/                  存储端接口 Writer 与分发器
    tdengine/               TDengine 宽表写入：建表、自动加列、批量 INSERT、不可用时丢弃

deploy/                     install.sh、kx-opc-client.service
scripts/                    build.sh

```

## 新增存储端（如 MySQL）

采集只有一份，存储端都挂在分发器后面。新增存储端时，采集、TDengine 相关的代码都不用动：

1. 新建 `internal/storage/mysql/`，实现 `storage.Writer`：
   ```go
   Name() string                  // 日志里显示的名字
   Accept(f model.Furnace) bool   // 要哪些炉台，比如只要配置里指定的炉台号
   Run(in <-chan model.Snapshot)  // 写入循环；in 关闭后写完剩余数据再返回
   ```
2. 在 `config.yaml` 里加一个 `mysql:` 节（连接串、要采集的炉台等）；
3. 在 `internal/app/app.go` 里把它传给 `storage.Start(log, tdWriter, mysqlWriter)`。

每个存储端都有独立的队列：MySQL 变慢或故障，只会丢它自己的数据，不影响采集，也不影响 TDengine。
